# Hierarchy Graph Visualizer Plan

## Goal

Build a Lean-generated hierarchy graph for the split algebraic hierarchy in
`NumLean/Interfaces/Algebra`. The graph should be exportable to JSON and visualizable in an
interactive ProofWidgets panel.

The graph is a hypergraph:

- Class declarations are nodes.
- Class inheritance and class assumptions are ordinary directed edges.
- Instance declarations are hyperedges from direct input classes to one output class.

## Attribute API

Add an attribute for explicitly selecting declarations that participate in the graph:

```lean
@[hierarchy_graph]
@[hierarchy_graph algebra]
```

The optional tag filters graphs, so we can generate smaller views such as only the algebra hierarchy.

Use a `SimpleScopedEnvExtension` to store entries:

```lean
structure HierarchyGraphEntry where
  declName : Name
  tag? : Option Name
```

This explicit marking is important because files such as `RCLike` contain related declarations and
instances that may or may not belong in a given visualization.

## Graph Data Model

The JSON should be generated by `deriving ToJson` on the graph structures, not by handwritten JSON
encoders.

Suggested Lean structures:

```lean
inductive HierarchyEdgeKind where
  | extends
  | assumes
deriving Repr, BEq, ToJson, FromJson

structure HierarchyClassNode where
  name : Name
  label : String
  type : String
  tag? : Option Name
deriving Repr, ToJson, FromJson

structure HierarchyClassEdge where
  source : Name
  target : Name
  kind : HierarchyEdgeKind
deriving Repr, ToJson, FromJson

structure HierarchyInstanceEdge where
  name : Name
  label : String
  inputs : Array Name
  output : Name
  type : String
  priority? : Option Nat
  tag? : Option Name
deriving Repr, ToJson, FromJson

structure HierarchyGraph where
  classes : Array HierarchyClassNode
  classEdges : Array HierarchyClassEdge
  instances : Array HierarchyInstanceEdge
deriving Repr, ToJson, FromJson
```

If deriving `ToJson` for `Name` is not available or produces awkward output, switch fields that cross
the JavaScript boundary to strings. Still keep `deriving ToJson` on the final structures.

## Class Dependency Extraction

For each marked class declaration:

- Add a `HierarchyClassNode`.
- Extract direct structure/class parents and add `extends` edges.
- Telescope the class declaration type.
- For each instance-implicit binder whose type is a class application, add an `assumes` edge.

Example:

```lean
class LawfulRingOps (K : Type u) [RingOps K] : Prop extends
    LawfulSemiringOps K, LawfulAddGroupOps K
```

Expected edges:

```text
LawfulRingOps --extends--> LawfulSemiringOps
LawfulRingOps --extends--> LawfulAddGroupOps
LawfulRingOps --assumes--> RingOps
```

The extraction should handle multi-parameter applications such as:

```lean
[NormedFieldOps RR R]
[NormedRingOps RA A]
[NormedAlgebraOps R A]
```

The initial graph can identify nodes by class name, but the node/type payload should retain enough
pretty-printed information to debug parameterized applications.

## Instance Hyperedge Extraction

For each marked instance declaration:

- Telescope the instance type.
- Collect instance-implicit class binders as direct `inputs`.
- Collect the final result class as `output`.
- Store the declaration name, type string, optional priority, and tag.

Example:

```lean
instance instCommRingOfOps {K : Type u} [RingOps K] [LawfulRingOps K] : CommRing K
```

Expected hyperedge:

```text
instCommRingOfOps: [RingOps, LawfulRingOps] ==> CommRing
```

The visualizer should treat instances as hyperedges, not as normal class nodes.

## Core API

Provide graph generation functions:

```lean
def generateHierarchyGraph (tag? : Option Name := none) : CoreM HierarchyGraph
def generateHierarchyGraphJson (tag? : Option Name := none) : CoreM Json := do
  return toJson (← generateHierarchyGraph tag?)
```

Add commands for inspection and visualization:

```lean
#hierarchy_graph_json
#hierarchy_graph_json algebra
#visualize_hierarchy_graph
#visualize_hierarchy_graph algebra
```

The JSON command is useful for debugging extraction independently of the widget.

## Visualizer Behavior

Add a hierarchy graph visualizer to the existing `NumLean.Meta.Visualize` / `js/visualize.js`
infrastructure.

Visual model:

- Every visible node is a class.
- `extends` edges use one visual style, for example solid blue arrows.
- `assumes` edges use another visual style, for example dashed amber arrows.
- Instances appear in a side panel after selecting a class, not as permanent graph nodes.

Interactions:

- Clicking a class selects it.
- The side panel lists instances whose `output` is the selected class.
- Clicking an instance highlights only direct dependencies:
  - the output class,
  - the direct input classes,
  - the selected instance entry in the side panel.
- Do not compute or display transitive inference closure in the first version.

Direct-only highlighting is intentional. Transitive closure might be useful later, but it can be more
expensive and may require semantics closer to Lean instance search.

## Hyperedge Rendering

For selected instances, render the hyperedge conceptually as an instance chip:

```text
RingOps ─┐
         ├─ instCommRingOfOps ─▶ CommRing
LawfulRingOps ─┘
```

In the first UI, it is enough to highlight the direct input/output class nodes and show the instance
in the side panel. A later UI can add explicit in-graph instance chips if needed.

## Initial Marking Scope

Start by marking a small subset in `NumLean/Interfaces/Algebra`:

- `*Ops` classes,
- `LawfulData*Ops` classes,
- `Lawful*Ops` classes,
- bridge instances between NumLean classes and mathlib classes.

Once extraction and visualization work on this subset, expand the markings across the full algebra
hierarchy.

For `RCLike`, decide explicitly whether to include non-core targets such as `CompleteSpace`,
`DecidableEq`, `StarRing`, and helper definitions. The attribute-based registry should make this a
local choice per declaration.

## Suggested Implementation Order

1. Add graph data structures with `deriving ToJson`.
2. Add the `@[hierarchy_graph <tag?>]` registry.
3. Implement class node extraction.
4. Implement `extends` edge extraction.
5. Implement `assumes` edge extraction from instance-implicit class binders.
6. Implement instance hyperedge extraction.
7. Add `generateHierarchyGraph` and JSON inspection commands.
8. Add `Visualize.HierarchyGraph` and a `#visualize_hierarchy_graph` command.
9. Extend `js/visualize.js` with the interactive class graph renderer.
10. Mark a small algebra subset and test.
11. Expand markings across the algebra hierarchy.
